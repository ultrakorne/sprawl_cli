# Item State & PR Number — Technical

## Architecture

Two additive fields on `client.ChecklistItem`, one dedicated write route, one new cross-task read, and rendering changes in every surface that already displayed items.

`internal/client/client.go` owns the transport (`SetChecklistItemState`, `ListChecklistItemsByState`), the three state constants and their `ValidState` guard, and `PRURL` — the single place a PR link is assembled. `internal/cli/checklist.go` adds the `state` / `pr` subcommands plus the shared item-trailer and label renderers; `internal/cli/queue.go` is the standalone top-level command. The TUI reaches the same route through its `Client` interface, so nothing in `internal/tui` talks to `net/http` directly.

## Wire Shapes

- **On every item payload**: `state` (string, nullable) and `pr_number` (integer, nullable). Both decode to their **zero value** rather than a pointer — `""` and `0`. That is safe because the server rejects a `pr_number <= 0`, so `0` can never be a real value, and it keeps every caller off pointer juggling. The renderers map the zero value back to a literal JSON `null`, so the key is always present in json output and a consumer never has to distinguish absent from cleared.
- **Write**: `PATCH /api/v1/checklist_items/:id/state`. The body is **flat** — `{"state": …}` and/or `{"pr_number": …}` — *not* wrapped in a `checklist_item` envelope, unlike `UpdateChecklistItem`. An **absent key means "leave unchanged"; a key present with `null` clears the field.** Response is the usual `{"checklist_item": {…}}`. Errors: 422 `invalid_state` / `invalid_pr_number` / neither key present, plus the usual 404 / 403.
- **Read**: `GET /api/v1/checklist_items?state=<state>`, envelope `{"tasks": [...]}`. `state` is required and must be one of the three. Each element is a trimmed task — `id`, `title`, `description`, `due_date`, `project` — with its matching items under `checklist_items` (ordinary item shape, no task stub), oldest task first, items in position order; a task with no item in the state is absent. `?full=true` inlines each item's `notes`. No `completed` filter exists or is needed — completing an item clears its state server-side. Decoded into `[]*client.QueueTask`; the CLI re-emits the same grouping with each item passed through `itemMap`.
- **`project` gains `key` and `github_url`** on every task payload (and on the `whoami` project block). `github_url` is validated server-side to be exactly `https://github.com/<owner>/<repo>` — no trailing slash, no `.git` — so `PRURL` concatenates without normalising. Empty covers both "no repo" and "pre-rollout server that omits the key".
- **`queue` adds one key the server does not send**: `pr_url`, the resolved link, `null` whenever any link in the chain is missing. Building it in the client is the point of `github_url` riding along on the nested project — otherwise every consumer reimplements the concatenation and the "render it unlinked" fallback.

## Noteworthy Behavior

- **Setting a state un-completes the item, server-side.** Every caller must treat the response as authoritative about `completed` too, and recompute anything derived from it. The TUI does this in `replaceItem`, which also re-syncs the parent task's progress on the list screen behind it.
- **The mirror image: completing an item clears its state.** The TUI's optimistic toggle drops the state locally the moment the box is ticked, so the icon doesn't linger on a row that is already done — and `itemToggledMsg` then applies the server's whole item through `replaceItem` rather than copying `completed` out of it. Copying two fields by hand was the original bug: the server said `state: null`, the reducer ignored it, and the stale icon survived until some other read refetched the task. The revert path carries `prevState` alongside `prev` so a rejected toggle puts both back. Unchecking does **not** restore a state — the server doesn't remember one.
- **The TUI's state cycle is optimistic; its failure path is a re-fetch, not a revert.** Because state and completion interact server-side, a remembered "previous value" is not trustworthy after a rejection — the failure handler re-reads the task instead. The optimistic local write is what lets repeated `s` presses advance the cycle rather than re-sending the same next-state from a stale value.
- **The PR write is not optimistic.** There is nothing to keep in sync between rapid keypresses, so the local copy is updated only when the server confirms.
- **`replaceItem` preserves the loaded note body.** Single-item write responses (title, state, PR) never carry `notes`, so taking the response verbatim would blank the note screen. This was previously inlined in the title-update path; the state work generalised it.
- **The TUI's state and PR columns are always reserved, never sized to what's on screen.** An earlier version collapsed the state column when no item used one; that made every row jump sideways the moment you pressed `s`, which is worse than a few dead cells. `stateColW` is a constant (every glyph in both icon sets is one cell) and `prColMinW` is a floor that only grows if a wider number is visible — and then it grows for every row at once. Padding is by display width (`padVis`), not rune count: the glyphs are four-byte, one-cell runes, so a byte- or rune-based measure reports a shift the terminal doesn't show. The tests measure title positions with `lipgloss.Width`, for the same reason.
- **The state glyphs are Nerd Font Material Design Icons**, the same family as the web app's pills (`md-hand_back_right`, `md-hammer_wrench`, `md-eye`). They are Private-Use-Area glyphs, so unlike emoji they carry no colour of their own and inherit the terminal foreground — which is what lets them be tinted from the ANSI palette like everything else in the TUI. `SPRAWL_ICONS=plain` swaps in geometric shapes for terminals with no patched font, where the default set would render as tofu.
- **Rows carry the icon only; the full name is spelled out in the item header.** A row has no room for `In progress` next to a title, and the icon column has to stay one cell wide to be stable. Opening the item (`enter`) shows `󱌣 In progress · PR #412` in the header, using the web app's own pill labels. The header labels the number `PR #412` where the row shows a bare `#412` — a column needs no label, a free-floating number does.
- **PR numbers are OSC 8 hyperlinks** (`linkPR`), so they open on click without the TUI capturing the mouse. The escape sequences are zero-width, and `ansi.Truncate` keeps them balanced when a line is clipped — verified by test at several widths, because an unbalanced sequence would hyperlink the rest of the screen. The link is applied *before* padding so only the number is clickable, not the blank cells aligning the column.
- **`prField` colours a PR number only when the link resolves** (underlined accent, the terminal's own convention). An unresolvable one — no project, or no repo URL — stays faint and unlinked, so the styling is a promise that clicking does something rather than decoration. On the selected row the colour switches to the selection's, but the **underline stays**: a link that stops looking like a link when the cursor lands on it reads as a glitch.
- **Order matters: the hyperlink wraps the styled text, never the reverse.** `lipgloss.Render` treats an OSC 8 escape in its input as literal text and styles it per character, which prints the URL on screen. That constraint propagates: `frame` no longer styles the title (callers pass one through `heading()`, and the item header appends its link-styled PR afterwards), and `rowLines` applies its style to the title only, leaving the prefix — which holds the linked PR cell — verbatim for the caller to style cell by cell. That last change is invisible because the selection style is bold + foreground with no background, so per-cell and per-line styling render identically. `TestScreens_NeverLeakLinkEscapes` guards the whole class: no rendered screen may show `]8;;` or a bare `https://` in its stripped text.
- **The item trailer is empty when both fields are unset**, which is what keeps the CLI's one-line item renderings unchanged for the overwhelming majority of items.
- **PR links resolve only where the project is in hand.** `task <id>`, `item <id>` and `queue` all carry a project (the task's own, the parent-task stub's, or the queue group's), so all three render the `PR` cell as an OSC 8 hyperlink over the bare `#412` text — the number stays short, the link rides invisibly. Write responses carry no task and therefore no project, so `renderItemWrite` passes a nil project and emits `pr_url: null` rather than inventing a link.
- **Clipboard Markdown matches the server's export format byte for byte**: a trailing `<!-- state: … pr: … -->` HTML comment on the checklist line, which renders as nothing and round-trips through the server's Markdown import. Items with neither field carry no comment, so existing copy output is unchanged. The whole-task copy names the repo once in its header rather than repeating it per item; the single-item copy names the resolved PR URL, since that is the one case where a bare `pr:` number has nothing to resolve against.
- **Validation is local wherever the rule is knowable.** `parseState` owns the alias vocabulary (a CLI concept the server has never heard of), and both the CLI and the TUI refuse a non-positive PR number before sending. Unknown states from a *newer* server still pass through the renderers verbatim rather than being hidden.
- **`ActivityItemTask` was renamed to `ItemTask`.** The activity log and `item <id>` return an identical parent-task stub; see [activity](../activity/INDEX.md). The queue does not use it — its groups are `QueueTask`, which also carries the description and due date.

## Dependencies

- Server-side enforcement of state/completion exclusivity, the `github_url` format, and the `pr_number > 0` rule. The CLI mirrors the last two locally for a better error, but does not re-implement the first.
- Project confinement and the readability cascade apply to `queue` exactly as to every other list endpoint — see [auth-and-config](../auth-and-config/INDEX.md).
